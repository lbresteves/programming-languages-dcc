## Questão 1 — A complexidade de `max`

**Assunto:** modelo de custo, casamento de padrões e `let` (Aula 06) · **Tipo:** rastreio + implementação

```sml
fun max [e] = e
  | max (h::t) = if max t > h then max t else h
```

> (a) Por que `match nonexhaustive`? (b) Qual termina mais rápido, `max [9, 8, ..., 1]` ou
> `max [1, 2, ..., 9]`? (c) Quantas chamadas em cada caso? (d) Reescreva em O(N), no melhor e
> no pior caso.

<details>
<summary>Resposta</summary>

**(a)** Nenhum padrão casa com a **lista vazia**: `[e]` exige exatamente um elemento e `h::t`
exige uma lista não vazia. `max []` lança a exceção `Match` em tempo de execução.

**(b)** A **primeira**, `max [9, 8, 7, 6, 5, 4, 3, 2, 1]`.

**(c)** `max t` só é chamado **duas vezes** quando `max t > h` é verdadeiro.
- Ordem **decrescente**: a cabeça é sempre maior que o máximo da cauda, a condição é sempre
  falsa, e há **uma** chamada por nível: C(N) = C(N − 1) + 1 = **N** chamadas (9).
- Ordem **crescente**: a condição é sempre verdadeira, e cada chamada gera **duas**:
  C(N) = 2 C(N − 1) + 1, com C(1) = 1, dá **2ᴺ − 1** chamadas (511).

**(d)**

```sml
fun max [e] = e
  | max (h::t) =
      let
        val m = max t
      in
        if m > h then m else h
      end;
```

`max t` é calculado **uma vez** e guardado em `m`: uma chamada por nível, O(N) para
qualquer entrada.

**Por quê:** o custo exponencial vem de **recalcular** o mesmo valor. O `let` dá um nome ao
resultado e o reutiliza. É a mesma técnica que leva o Fibonacci de exponencial a linear.

</details>

## Questão 2 — Uma gramática de expressões booleanas

**Assunto:** ambiguidade e precedência (Aulas 02–03) · **Tipo:** conceitual + implementação

```
<E> ::= <E> and <E>
      | <E> or <E>
      | not <E>
      | true
      | false
```

> (a) Demonstre que é ambígua. (b) O que é precedência relativa? (c) Operadores mais perto
> ou mais longe do símbolo de partida têm precedência maior? (d) Faça `and` ter precedência
> maior que `or`.

<details>
<summary>Resposta</summary>

**(a)** A sentença `true and false or true` tem duas árvores:

```
          E                           E
       /  |  \                     /  |  \
      E   or  E                   E  and  E
    / | \     |                   |     / | \
   E and E   true               true   E  or E
   |     |                             |     |
 true  false                         false  true

 (true and false) or true      true and (false or true)
        = true                        = true
```

(Com `false and false or true`, os dois significados dão valores diferentes: `true` e
`false`.)

**(b)** É a regra que diz **qual operador agrupa primeiro** quando dois operadores
diferentes aparecem sem parênteses. Se `and` tem precedência maior que `or`,
`a or b and c` significa `a or (b and c)`.

**(c)** Os gerados por produções **mais distantes** do símbolo de partida. Eles ficam mais
perto das **folhas**, então são agrupados (avaliados) primeiro.

**(d)** Um não-terminal por nível de precedência, com o `and` **abaixo** do `or`:

```
<E> ::= <E> or <T>
      | <T>
<T> ::= <T> and <F>
      | <F>
<F> ::= not <F>
      | true
      | false
```

**Por quê:** a ambiguidade vem de `<E> op <E>`, que permite recursão dos dois lados e mistura
os dois operadores no mesmo nível. Separar os níveis resolve a **precedência**; fazer a
recursão de um lado só resolve a **associatividade** (aqui à esquerda).

</details>

## Questão 3 — Formas de execução

**Assunto:** compilação, interpretação e *bytecode* (Aula 04) · **Tipo:** conceitual

> Uma linguagem executada principalmente (1) interpretando a árvore de sintaxe, (2) via
> *bytecode*, (3) compilada para código de máquina. Por que quase toda linguagem tem
> *parsing*? Uma razão para uma linguagem ser compilada.

<details>
<summary>Resposta</summary>

| Caminho | Linguagem |
|---|---|
| interpretação da árvore de sintaxe | **Bash** (também R e o Ruby antigo) |
| *bytecode* + máquina virtual | **Java** (também Python/CPython e C#) |
| código de máquina | **C** (também C++ e Rust) |

***Parsing*:** o programa chega como **texto**, uma sequência de caracteres. Para fazer
qualquer coisa com ele (interpretar, compilar, verificar tipos), é preciso descobrir a sua
**estrutura**: a árvore de sintaxe. Tanto um interpretador quanto um compilador precisam
dela, então o *parsing* está em todos os caminhos.

**Por que compilar:** **eficiência**. A tradução para código de máquina é feita **uma vez**,
antes da execução; interpretar repete a análise de cada comando toda vez que ele executa.
Também ajuda o fato de o compilador poder otimizar o programa inteiro e, em linguagens
estáticas, eliminar os testes de tipo.

</details>
