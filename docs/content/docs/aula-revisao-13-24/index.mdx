## Aula 13 — 30/09 · Registros de ativação

[Minhas anotações](/docs/aula-13) · Lista 13

- Arquitetura de von Neumann: onde ficam os valores.
- Ativação × registro de ativação; alocação estática (sem recursão) × pilha.
- Pilha corrompida.
- Funções aninhadas e o **link de aninhamento** (_nesting link_).
- Closures: quando o registro de ativação não pode ser desempilhado.

**Ênfase / pode cair:** funções aninhadas.

```python
def f(n):
    def g(m):
        return m + n
    return g(3)

f(4)    # devolve 7
```

Nesse caso, o difícil é encontrar o `n`: ele não está no registro de ativação de `g`, e sim
no de `f`. Para achá-lo, o registro de ativação de `g` guarda um ponteiro para o registro da
função **aninhadora** (`f`): é o **link de aninhamento** (_nesting link_).

</Callout>

**Ênfase / pode cair:** a passagem de parâmetros em Python é **por valor** (o valor copiado é
a referência ao objeto). Como se vê isso através de um programa?

```python
def muda_str(s):
    s = ""

s = "DCC024 eh muito legal"
muda_str(s)
print(s)    # DCC024 eh muito legal
```

Strings em Python não podem ser mudadas (são imutáveis).

```python
def muda_lista(L):
    L.append(1)

L = ["oi", "DCC024"]
muda_lista(L)
print(L)    # ['oi', 'DCC024', 1]
```

Por que `muda_lista` funciona e `muda_str` não? O parâmetro formal é uma **cópia** da
referência: os dois nomes apontam para o mesmo objeto. Em `muda_str`, `s = ""` só faz a
cópia local apontar para outro objeto, e o `s` de fora continua igual. Em `muda_lista`,
`L.append(1)` **muta o objeto** apontado, que é o mesmo visto de fora. Se `muda_lista`
fizesse `L = []`, também não mudaria nada fora. Ver a [Aula 19](/docs/aula-19).

## Aula 15 — 07/10 · Gerenciamento de memória

[Minhas anotações](/docs/aula-15) · Lista 15

- As três áreas: memória **estática**, **pilha** e **heap**.
- Quando cada valor é alocado e liberado.
- Erros de gerenciamento de memória (vazamento, ponteiro pendente).
- Coleta de lixo.

**Ênfase / pode cair:** coletor de lixo (_garbage collector_).

- Temos algumas linguagens com coleta de lixo e outras sem. C, por exemplo, não tem; nem
  C++, Pascal, Fortran — linguagens mais antigas (apesar de que Rust, mais nova, também não
  tem). Nesse caso é preciso dar `free`: liberar a memória é papel do programador.
- Qual a vantagem disso? **Eficiência**: coleta de lixo é lenta.
- O problema: dar `free` numa variável e usá-la de novo depois (ponteiro pendente).
- As chaves `{ }` em C fazem pouca coisa (só delimitam o escopo), mas em C++, por exemplo,
  o fim do bloco chama os **destrutores** dos objetos locais.
- **Memória alcançável:** o coletor só libera o que não é alcançável. Memória alocada
  estaticamente é alcançável, e a alocada localmente (na pilha) também; elas são as
  **raízes** a partir das quais se seguem os ponteiros do heap.

Formas de coleta de lixo: comentamos duas, **marcação e varredura** (_mark and sweep_) e
**contagem de referências** (_reference counting_). Marcação e varredura tem uma vantagem
sobre contagem de referências: lida com **ciclos** (estruturas que apontam umas para as
outras têm contador sempre maior que zero, mesmo inalcançáveis).

O coletor de lixo de Python (CPython) funciona por **contagem de referências**, com um
coletor de ciclos à parte para resolver justamente esse problema.

## Aula 16 — 19/10 · TADs

[Minhas anotações](/docs/aula-16) · Lista 16

- O que é um tipo abstrato de dados; Barbara Liskov.
- Por que encapsular: o custo de alterar software.
- TADs em C (`.h` e `.c`), SML (`signature` e `structure`), Java (interfaces) e Python
  (classes, sem `private` de verdade).
- Estendendo um TAD.

**Ênfase / pode cair:**

- Uma grande vantagem é que ele é uma forma de **encapsular dados**, e isso é importante

## Aula 17 — 21/10 · Programação orientada a objetos

[Minhas anotações](/docs/aula-17) · Lista 17

- O que é POO; história (Simula 67, Smalltalk, Java).
- Classe, objeto, herança.
- **Sobrecarga × sobrescrita**.
- **Ligação dinâmica** (despacho dinâmico); tipo estático × tipo dinâmico; Liskov.
- Custo da chamada: _vtable_ O(1) em Java/C++ × busca por nome em Python.
- Procedural × OO: o problema da expressão.

**Ênfase / pode cair:**

- Em Python tudo é tabela, tudo é dicionário. Uma forma comum de estender código é usando
  herança; em Python, como tudo é dicionário, também se pode simplesmente adicionar mais um
  valor (campo ou método) a um objeto ou classe em execução.
- POO é bem diferente de programação procedural, mas em que sentido? A procedural é
  **top-down**; a POO é mais **bottom-up**, como um grafo que começa desconexo e vai ficando
  conexo.
- Não há como fazer isso em C: uma `struct` não é uma tabela hash, e não dá para incluir
  campos nela em execução. C é muito pouco orientada a objetos: numa lista encadeada em C, a
  lista não faz nada; quem faz são as funções que a recebem.

<Callout title="Cai em prova: 37,5% (provas 22, 24 e 28)" type="warn">
  Formato: "por quê" sobre POO — qual versão é OO e qual é procedural e qual é mais fácil de
  estender; sobrecarga é polimorfismo _ad hoc_ ou universal; o que é `virtual` e por que a
  chamada é O(1) em C++ e não em Python. Exemplo: prova 28, Q1d (alvo de chamada virtual em
  O(1) em C++, mas não em Python). Pegadinha: OO facilita acrescentar **um novo tipo** de nó;
  procedural facilita acrescentar **uma nova operação** (prova 22, Q2b e Q2c). Ver Tópico 3
  do `material/provas-antigas/2a-prova/compilado-de-questoes.md`.
</Callout>

## Aula 18 — 26/10 · Tratamento de erros

[Minhas anotações](/docs/aula-18) · Lista 18

- Opções para o erro no `pop`: definição total, erro fatal, guardas, sinalização de erro.
- Pré e pós-condições (Eiffel).
- Tipos `result` e mônadas.
- Exceções: hierarquia de `Throwable` em Java, `finally`, exceções e tipagem forte.

**Ênfase / pode cair:**

- C não tem exceções: podemos tratar erros com **valores especiais** (ex.: devolver `-1` ou
  `NULL`).
- O principal mecanismo de tratamento de erros é o **sistema de tipos**, impedindo que eles
  aconteçam. O cálculo lambda (não tipado), por exemplo, não tem verificação de tipos: como
  não há tipos ali, posso passar para `SUCC` algo que não é um numeral de Church. O sistema
  de tipos restringe como se escreve o programa, e é isso que evita o erro.
- Rust não tem coleta de lixo, mas não tem a possibilidade de dar `free` e usar a memória
  depois (nem de liberar duas vezes). Isso ocorre porque o sistema de tipos é mais
  restritivo (posse e empréstimo: o compilador sabe quando cada valor morre).

## Aula 21 — 09/11 · Modelos de custo

[Minhas anotações](/docs/aula-21) · Lista 22

- Arranjos (acesso O(1)) × listas encadeadas de LISP/SML/Prolog (`hd`/`tl` O(1)).
- Custo de `append` em Prolog: proporcional à **primeira** lista.
- Custo da unificação: proporcional ao tamanho da estrutura.
- `reverse` quadrático × linear com acumulador.
- **Recursão de cauda** (_tail recursion_) e registros de ativação.

**Ênfase / pode cair:**

- Modelos de custo das listas encadeadas, que vêm de LISP.
- As formas como acesso os arranjos. Imagine um arranjo grande que quero somar. Tenho um
  algoritmo que soma do início ao fim e um que escolhe posições aleatórias. Assuma que
  escolher a posição aleatória seja O(1) e que ela não se repita. Sabemos que, mesmo assim,
  o aleatório **não** é mais rápido (na prática é mais lento), por causa da **localidade de
  referência** e da **cache**: quando leio um dado, a chance de eu ler o próximo dado é
  muito grande, e ele já veio para a cache junto.
- O mesmo vale para matrizes em C, que são guardadas por linhas: percorrer `m[i][j]` com `j`
  no laço de dentro é sequencial na memória; com `i` no laço de dentro, cada acesso salta
  uma linha inteira.
- Redes neurais fazem muito isso de melhorar a localidade de referência: o que elas mais
  fazem é multiplicar matrizes, então muitas das otimizações são de localidade em matrizes.


## Aula 23 — 16/11 · Semântica formal

[Minhas anotações](/docs/aula-23) · Lista 24

- Sintaxe parecida, semântica diferente: `x += (x = 2)` em C × Java.
- Semântica denotacional, axiomática e operacional.
- Passo longo × passo curto; regras de inferência (`IF_T`, `IF_F`) e prova de equivalência.
- Interpretador em Prolog: AST, contexto (`bind`), `let`, `fn`/`apply`.
- Escopo dinâmico (`val3`) × estático com closure (`val4`); recursão com `fun`.

**Ênfase / pode cair:** diferença entre escopo estático e escopo dinâmico.

```sml
let
  val one = 1
in
  let
    val f = fn x => x + one
  in
    let
      val one = 2
    in
      f(3)
    end
  end
end
```

Em SML, que tem escopo estático, esse programa dá **4** (não 5): `f` é avaliada no contexto
em que foi **criada**, onde `one = 1`. Com escopo dinâmico (o `val3`), daria 5, porque o
`one` seria procurado no contexto de quem chama, onde a ligação mais recente é `one = 2`.

Isso é o **closure**: o par (código + valores das variáveis livres no momento em que a
função foi criada).

<Callout title="Cai em prova: 25% (provas 22 e 29)" type="warn">
  Formato: escrever, numa linguagem dada, um exemplo de closure, de polimorfismo paramétrico
  ou de casamento de padrões, ou reconhecer um closure numa sintaxe desconhecida. Exemplo:

  Pegadinha: na prova 22, Q2d, o closure aparece em Kotlin (`{ acc, i -> insert(acc, i) }`
